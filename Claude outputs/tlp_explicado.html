Tu proyecto de TLP, explicado desde cero

Cada sección construye sobre la anterior. Lee en orden y juega con los simuladores. Al final hay preguntas tipo defensa para practicar.

La pregunta del proyecto en una frase: con las mismas reglas que usamos para describir un lenguaje de programación, ¿se puede describir el español? ¿Hasta dónde llegamos y en qué punto fallamos?

Para responderla hicieron tres cosas: (1) un analizador para un C chiquito («Mini-C»), donde todo funciona perfecto; (2) el mismo tipo de analizador para un pedazo del español, anotando dónde falla y por qué; (3) una comparación con dos herramientas reales, NLTK y spaCy.

1¿Qué es un «lenguaje» para un informático?

En la vida diaria un lenguaje es algo que hablamos. En esta materia es algo mucho más simple y frío:

Un lenguaje es un conjunto de cadenas. Nada más. Por ejemplo, «todas las cadenas de C que compilan» es un lenguaje, y «todas las oraciones correctas del español» es otro.

¿Cómo describes un conjunto que tiene infinitas cadenas? No puedes escribirlas todas. Lo que haces es escribir reglas que las generan. A ese conjunto de reglas se le llama gramática.

Piensa en una receta:

Oración  →  Sujeto  Verbo
Sujeto   →  "el gato"  |  "la niña"
Verbo    →  "duerme"   |  "corre"

La flecha → se lee «se puede reemplazar por» y la barra | significa «o». Partiendo de Oración y reemplazando, puedes obtener «el gato duerme», «la niña corre», etc. A las cosas con mayúscula (Oración, Sujeto) se les llama no terminales, porque todavía hay que reemplazarlas. A las palabras finales («gato», «duerme») se les llama terminales.

Un programa que recibe una cadena y responde «sí, esto sigue las reglas» (o «no, y el error está aquí») se llama analizador o parser. Eso es lo que construyeron.

Para la defensa: «Una gramática es un conjunto finito de reglas que describe un lenguaje posiblemente infinito. El parser decide si una entrada pertenece a ese lenguaje y, si pertenece, construye su árbol de análisis».

2La jerarquía de Chomsky: «qué tanta memoria necesitas»

No todos los lenguajes son igual de difíciles. Chomsky los ordenó en 4 niveles. La forma más fácil de entenderlo es así: cada nivel necesita una máquina con más memoria para reconocerlo.

Cada caja contiene a la de adentro. Tu proyecto vive sobre todo en las cajas verde y azul, y discute el borde con la morada.

Simulador: ¿por qué los paréntesis necesitan una pila?

Un autómata finito solo tiene una cantidad fija de estados. Es como alguien que cuenta con los dedos de una mano: llega hasta un límite y después se pierde. Un autómata de pila tiene una pila de platos: por cada ( pone un plato y por cada ) quita uno. La pila puede crecer todo lo que haga falta.

Aquí el autómata finito solo puede «contar» hasta 3. Prueba con 4 o más paréntesis anidados:

Por eso Mini-C no es regular (Tipo 3), sino libre de contexto (Tipo 2). En nuestro parser, la pila de llamadas recursivas cumple el papel de la pila del autómata». 3El lexer: de letras sueltas a «palabras» (tokens)

La computadora recibe el programa como una tira de caracteres: i, n, t, espacio, x… Antes de entender la estructura, hay que agrupar esas letras en piezas con significado. A esas piezas se les llama tokens. Es como separar una oración en palabras antes de analizar la gramática.

4La gramática de Mini-C: las «recetas»

Ahora que tenemos tokens, falta decir en qué orden pueden aparecer. Estas son las reglas reales de su proyecto (están en gramatica.py, en un diccionario llamado GRAMATICA):

Programa → Stmts                         (un programa es una lista de sentencias)
Stmts    → Stmt Stmts | ε                (ε = "nada", la lista puede acabar)
Stmt     → int ID Init ;                 (declaración:  int x = 5;)
         | ID = Expr ;                   (asignación:   x = x - 1;)
         | if ( Cond ) Bloque Else       (if con else opcional)
         | while ( Cond ) Bloque
         | print ( Expr ) ;
         | Bloque
Init     → = Expr | ε
Else     → else Bloque | ε
Bloque   → { Stmts }
Cond     → Expr CondR        CondR → RELOP Expr | ε
Expr     → Term ExprR        ExprR → + Term ExprR | - Term ExprR | ε
Term     → Factor TermR      TermR → * Factor TermR | / Factor TermR | ε
Factor   → NUM | ID | ( Expr ) | - Factor

Tres trucos de diseño que te van a preguntar

① Precedencia por «pisos». Una expresión (Expr) se arma con sumas de términos. Un término (Term) se arma con multiplicaciones de factores. Un factor es un número, una variable o algo entre paréntesis. La multiplicación vive en un piso más abajo, así que en el árbol queda más abajo y se calcula primero. Lo vas a ver en vivo en el simulador de la sección 5.

② Sin recursión izquierda. La forma «natural» de escribir la suma sería Expr → Expr + Term. Pero el parser de ustedes funciona con una función por regla: expr() llamaría a expr(), que llamaría a expr()… sin leer ningún token. Sería un bucle infinito. Por eso se reescribe como Expr → Term ExprR: primero se lee un término y luego «el resto» (ExprR).

③ Llaves obligatorias. En C real, en if (a) if (b) x=1; else x=2; no queda claro de cuál if es el else. A eso se le llama el «else colgante». En Mini-C if y while siempre llevan { }, así que esa duda nunca aparece.

¿Qué es ε? Es la cadena vacía. Init → = Expr | ε significa «después del nombre puede venir = valor, o nada». Así se escriben las partes opcionales.

5El parser, paso a paso (simulador principal)

El parser de ustedes es descendente recursivo. Hay una función por cada no terminal: stmt(), expr(), term(), factor()… Cada función sigue su regla: si la regla dice «aquí va un Term», llama a term(); si dice «aquí va un ;», llama a consumir(';').

  • lookahead (en el código, self.la): el token que el parser está mirando en este momento. Es el único que mira.
  • consumir(tipo): «espero este tipo de token». Si llega, avanza al siguiente; si no, lanza un error con línea y columna.
  • pila de llamadas: qué funciones están «abiertas» en este momento. Fíjate cómo crece y se vacía. Esa es la pila del autómata de pila.

    La misma corrida como tabla: traza LL(1) (pila · entrada · acción)

    El simulador de arriba muestra la pila de llamadas. Hay otra forma de ver exactamente lo mismo, que seguramente vieron en clase: una tabla con una pila explícita, la entrada que falta y la acción de cada paso. Usa el mismo código que cargaste arriba.

    ¿Y shift / reduce? No se usan aquí. Shift y reduce son las acciones de los parsers ascendentes (LR, SLR, LALR, como yacc o bison), que arman el árbol desde las hojas hacia la raíz. El parser de ustedes es descendente (LL): arma el árbol desde la raíz hacia las hojas, y sus acciones son otras:
    • Derivar: el tope de la pila es un no terminal. Se busca en la tabla M[tope, lookahead] qué regla usar y se reemplaza el tope por el lado derecho de esa regla.
    • Emparejar: el tope es un terminal igual al token de entrada. Se sacan los dos y se avanza.
    • Aceptar: la pila y la entrada llegan juntas a $.
    • Error: la celda de la tabla está vacía, o el terminal del tope no coincide con la entrada.
    Si en la defensa les preguntan por shift/reduce, la respuesta es: «nuestro parser es descendente LL(1), por eso sus acciones son derivar y emparejar; shift/reduce es de los parsers ascendentes LR».

    6LL(1), FIRST y FOLLOW: «¿me basta ver un token?»

    En el simulador habrás visto que en cada Stmt el parser decide qué regla usar con solo mirar el token siguiente. Eso no es suerte: la gramática se diseñó así a propósito.

    LL(1) significa: se lee de izquierda a derecha (L), se arma la derivación por la izquierda (L) y se mira 1 token adelante.

    FIRST: «con qué puede empezar»

    FIRST(X) es el conjunto de tokens con los que puede empezar X. Toca un token y mira qué regla de Stmt escogería el parser:

    Elige un token.

    Como cada alternativa de Stmt empieza con un token distinto, nunca hay que adivinar. Si dos alternativas empezaran con lo mismo, sería un conflicto y la gramática ya no sería LL(1).

    FOLLOW: «qué puede venir después»

    FOLLOW se necesita para las reglas que pueden ser ε (nada). Ejemplo: después de if (…) {…}, ¿viene un else o termina el if? El parser decide así: si ve else, usa Else → else Bloque; si ve otra cosa (algo que está en FOLLOW, como }, $ u otra sentencia), usa Else → ε. Funciona porque else no está en FOLLOW(Else).

    Cómo lo verifica el código

    calcular_first_follow() calcula los conjuntos «por punto fijo»: recorre todas las reglas una y otra vez, agregando tokens, hasta que en una vuelta completa nada cambia (es el while cambio: del código). Después, verificar_ll1() revisa cada par de alternativas:

    1. si sus FIRST se cruzan, hay conflicto;
    2. si una puede ser ε y la otra empieza con algo que está en FOLLOW, hay conflicto.

    Para Mini-C el resultado es 0 conflictos, y eso es lo que imprime python -m tlp.formal: «Gramática LL(1): SÍ».

    Para la defensa: «LL(1) significa que con un solo token de anticipación siempre sabemos qué producción aplicar. No lo afirmamos a ojo: verificar_ll1() calcula FIRST y FOLLOW sobre el mismo diccionario de la gramática y encuentra 0 conflictos». Si te preguntan por la debilidad: el parser se escribió a mano, no se genera de ese diccionario. Que corresponda a la gramática se comprueba con las pruebas, no automáticamente.

    7Ahora el español: ¿funciona la misma idea?

    Hicieron un segundo parser en gramatica_es.py. La gran diferencia con Mini-C es que en español las palabras tienen que concordar: «la gato» está mal, «los niño» está mal, «los niños duerme» está mal.

    El truco: rasgos

    Cada palabra del léxico (unas 181 formas) trae etiquetas: género (m/f), número (sg/pl), tiempo, tipo de verbo (transitivo, intransitivo, o que exige «que») y animacidad (humano, animal, cosa). La animacidad sirve para la «a personal»: se dice «ve a Juan», pero «ve el libro».

      La misma regla como CFG pura (sin rasgos)

      ¿Por qué esto importa? Las 10 reglas vs. las 338 producciones

      Con rasgos, la gramática es corta: 10 reglas. Pero alguien podría decir: «eso de revisar rasgos ya no es una CFG, es otra cosa». Para responder, la función cfg_nltk() expande los rasgos: en vez de una regla SN → Det N «que revisa el género», crea una regla por cada combinación, como SN_f_pl → Det_f_pl N_f_pl (lo ves en el panel de la derecha del juego). Como el género tiene 2 valores, el número 2 y la animacidad 3, las combinaciones son finitas. El resultado es una CFG normal de 338 producciones.

      Después le pasan las mismas oraciones a NLTK (que solo entiende CFG puras), y acepta exactamente lo mismo que su parser.

      Para la defensa (este es el argumento más fuerte): «La concordancia de género y número no saca al español de Tipo 2. Como los rasgos tienen valores finitos, se pueden convertir en no terminales. Eso cuesta tamaño de gramática (de 10 reglas pasamos a 338 producciones), pero no poder expresivo. NLTK lo confirma».

      ¿Por qué este parser es distinto al de Mini-C? Retroceso con yield

      En español, con un solo token muchas veces no se puede decidir. Ejemplo: después de «el hombre ve al gato», si llega «con…», ¿eso va con el gato o con el verbo ver? Las dos opciones son válidas. Por eso este parser no es LL(1), sino de retroceso:

      • Cada función es un generador (usa yield): en lugar de devolver UN análisis, va entregando todos los posibles, uno por uno.
      • Si un camino choca con algo (por ejemplo, la concordancia falla), se descarta y se prueba el siguiente.
      • Al final solo se quedan los análisis que consumieron la oración completa. Así pueden contar cuántos árboles tiene una oración.

      Diagnóstico: la función _fallo() recuerda la posición más lejana a la que llegó el parser y por qué falló ahí. Por eso los mensajes dicen cosas como: «falla en la posición 5 ('duerme'), regla concordancia sujeto–verbo: 'duerme' es sg pero el sujeto es pl».

      Subordinación: SV → V Que O permite «Pedro dice que Ana piensa que el gato duerme». Es recursiva, porque una oración puede contener otra oración. Rel → Que SV permite «el gato que duerme».
